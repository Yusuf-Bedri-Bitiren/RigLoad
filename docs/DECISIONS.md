# Decisions

| Date | Decision | Options | Choice | Reason |
|---|---|---|---|---|
| 2026-11-19 | Python version | 3.11 / 3.12 / 3.13 | 3.13 | Already installed; torch, torchvision, PyO3 and maturin all support it. |
| 2026-11-19 | GPU source | Own GPU / Colab / cloud / university cluster | Own RTX 3050 Laptop (4 GB) to start; university HPC (H100, L40, possibly H200) for larger runs | Local GPU is enough for early GPU steps; HPC jobs need permission and get scheduled when scale requires it. |
| 2026-11-19 | Torch build | CPU / CUDA | CUDA (cu130) | Ready for the GPU steps; driver 616.92 supports CUDA 13. |
| 2026-11-19 | License | MIT / Apache-2.0 / MIT OR Apache-2.0 | MIT OR Apache-2.0 | Rust ecosystem norm (PyO3, serde, rayon); Apache adds a patent grant, MIT keeps it simple for users. |
| 2026-11-19 | PyO3 version | — | 0.30 (latest) | `Python::detach` releases the GIL (renamed from `allow_threads`). |
| 2026-11-19 | `extension-module` feature | Always on in Cargo.toml / only in maturin builds | Only via `[tool.maturin] features` | With it on, `cargo test` can't link libpython. Maturin turns it on for wheels; plain cargo builds link normally. |
| 2026-11-19 | Python package layout | Pure Rust module / `python/` source + `rigload._rigload` native module | Mixed layout | Python wrappers and `.pyi` type hints live next to the native module; the native part stays private (`_rigload`). |
| 2026-11-19 | Positioning | Camera-only calibration-aware / LiDAR ↔ camera consistency as the main angle | LiDAR ↔ camera, built on the camera pipeline | Prior art (`PRIOR_ART.md`) is weakest on keeping LiDAR, image and calibration consistent at native speed. Claims follow benchmarks; pivot if data doesn't support it. |
| 2026-11-19 | Step order | Original (LiDAR last, stretch) / LiDAR right after camera transforms | 0–5 → 6 → 11 → 7–10 → 12 | Engine first, then the main angle early. Synthetic data includes LiDAR from Step 2. |
| 2026-11-19 | Second baseline | torchvision v2 only / + Albumentations | + Albumentations | It is the closest existing tool functionally; beating only torchvision would be a weak comparison. |
| 2026-11-19 | Sparse depth source | Random mask on dense depth / projected LiDAR | Projected LiDAR, nearest point per pixel | KITTI-like scan-line structure, and it ties depth, LiDAR, K and T together so calibration bugs show up. |
| 2026-11-19 | Pixel-centre convention | Integer centres (OpenCV/KITTI) / half-integer | Integer: `[u, v, 1]^T ~ K X` | Matches KITTI and OpenCV calibration files. A test detects a half-pixel error. |
| 2026-11-19 | Synthetic calibration | Fixed K and T / per-sample jitter | K ±2 % focal, ±5 px centre; T ±0.3° and ±1 cm | Code that uses the wrong sample's calibration fails the tests. |
| 2026-11-19 | Fixtures | 20 full / 8 full / 20 half-res | 20 samples, full-res images, LiDAR at 1° (8.1 MB) | Full-size images like KITTI; LiDAR density is the only size driver. |
| 2026-11-19 | Determinism scope | Bytes identical everywhere / same machine | Bytes identical on the same machine; fixtures compared with tolerances across machines | numpy transcendental functions and encoder builds may differ by platform in the last bit. |
| 2026-11-20 | Baseline augmentation | Various ranges; hue or not | Crop scale [0.8, 1] at the output aspect → resize 640×192 → hflip p = 0.5 → brightness, contrast, saturation ×[0.8, 1.2] in that fixed order; no hue; batch 32 | Hue needs an RGB↔HSV round trip and dominates CPU time while adding little for depth tasks. Rust must match these exactly (Step 6). |
| 2026-11-20 | How baselines draw parameters | Random `v2.Compose` / own draw + functional API | `bench/common.py: draw_params(seed, epoch, index)` + functional ops | Random Compose transforms hide their parameters, so K can't be updated. Same draw rule as the Rust pipeline. |
| 2026-11-20 | K update formulas | Edge convention (cx·s, W − cx) / integer centres | cx′ = (cx + 0.5)·s − 0.5; flip cx′ = W − 1 − cx with the scene mirrored | Matches the generator's integer pixel centres; verified exactly against torchvision and OpenCV pixel ops (test_baselines.py). |
| 2026-11-20 | torchvision depth resize | Default Mask NEAREST / NEAREST_EXACT | NEAREST_EXACT | The default (legacy floor-based nearest) picks pixels up to ~1 source pixel off what K says; it doubles the median LiDAR-on-depth error (0.25 % → 0.48 %, fixtures). Kept as a test that documents it. |
| 2026-11-20 | Albumentations package | albumentations 2.0.8 (MIT, no release since 2025-05) / albumentationsx 2.6.6 (AGPL-3.0) | albumentationsx, bench scripts only | Strongest maintained version to beat; rigload never imports it, so its license is unaffected. |
| 2026-11-20 | Albumentations API | `A.Compose` / functional kernels | Functional kernels with our parameters | Compose's applied-params record has no crop coordinates (K can't be updated), and building a Compose per sample cost ~14 ms, about as much as applying it. Skipping Compose makes this baseline slightly optimistic. |
| 2026-11-20 | RGB resize filter | Same filter in both / each library's default | torchvision bilinear + antialias (v2 default); Albumentations INTER_LINEAR (its default) | Benchmarks what users get by default. Depth is bit-identical between the two (both nearest-exact). |
| 2026-11-20 | Benchmark warm-up | Fixed 10 batches / scale with workers | max(10, 2 × workers) | On Windows each worker spawns and re-imports torch; a fixed warm-up let a still-starting worker leak into the timed window (p99 5.9 s in a smoke run). |
| 2026-11-20 | Worker sweep range + memory guard | 0–16 workers / 0–8 with a guard | `0,2,4,6,8`; a run aborts if available RAM < 1.5 GB and the sweep stops there; JSON saved after each worker count | Measured: each DataLoader worker (a process loading CUDA torch on Windows) commits 1.48 GB (0.64 GB resident). At 12 workers the 15.7 GB laptop hit its commit limit and froze the desktop, and those numbers were meaningless. |
| 2026-11-20 | Rust decode crates | `image` / `zune-jpeg` / `turbojpeg` (+ `png`) | `image` 0.25 with only `jpeg` + `png` features; **kept pure Rust after the Step 4 gate (user, 2026-11-20)** | Its JPEG decoder *is* zune-jpeg, so those two are one option. Clean numbers: JPEG 2.77 ms vs libjpeg-turbo (torchvision.io) 2.22 ms, but RGB + depth per sample 4.18 vs 4.63 ms (1.11× faster). libjpeg-turbo would save ~0.55 ms/sample at the cost of CMake + NASM in every wheel build and an unsafe C dependency. Revisit in the Step 9 ablation if JPEG decode is the bottleneck. |
| 2026-11-20 | Depth decode strictness | Convert any PNG to u16 / accept only 16-bit grey | Only 16-bit grey; anything else is an error | Silently rescaling 8-bit data would corrupt metric depth. |
| 2026-11-20 | Error type | `thiserror` / hand-written enum | Hand-written `Error { Io, Manifest, Decode }`, each with the file path | 40 lines, no dependency; every error names the file (and manifest line). |
| 2026-11-20 | NumPy handoff | Copy into new arrays / take ownership of the Vec | `numpy` 0.30 `PyArray1::from_vec` + `reshape` | No copy: the array is a view over the Rust buffer (tested via `OWNDATA`/`base`). |
| 2026-11-20 | RNG | `rand` + `rand_chacha` / own SplitMix64 | Own SplitMix64 (user), streams derived from (seed, epoch[, index]) | 15 lines, no dependency, portable and deterministic; verified against the reference C outputs. Draws differ from numpy's, so Step 6 compares transforms for identical parameters, not identical draws. |
| 2026-11-20 | Prefetch channel | `crossbeam-channel` / `std::sync::mpsc::sync_channel` | std `sync_channel(prefetch)` (user) | Bounded, single consumer is all we need; crossbeam's implementation is inside std since Rust 1.72. No dependency. |
| 2026-11-20 | Pipeline shape | Per-sample tasks across batches / one batch at a time | Producer thread decodes one batch at a time with `par_iter` on a dedicated rayon pool, then sends it | Simplest correct design. Threads idle while the slowest sample of a batch finishes; measure first, overlap batches later only if the benchmark shows it matters. |
| 2026-11-20 | Shutdown | Detach thread / stop flag + drop receiver + join | Drop sets a stop flag, drops the receiver (a blocked `send` fails), then joins | Never hangs: at most one in-flight batch finishes. A producer panic is reported as an error, not a silent end of epoch. |
| 2026-11-20 | Batch layout | NCHW / NHWC | NHWC uint8, depth (B,H,W) uint16, K (B,3,3), moved into NumPy without copy | Matches decode output, no transpose. NCHW and dtype are Step 7 decisions. One memcpy per sample into the batch buffer remains (noted in code). |
| 2026-11-20 | Python iterator thread safety | `unsendable` pyclass / `Mutex` | `Mutex<EpochIter>` | PyO3 classes must be `Sync`; a `Receiver` is only `Send`. The mutex makes it shareable, and is uncontended in normal use. |
| 2026-11-20 | Memory-guard repeats | Discard / keep repeats completed before the stop | Keep, marked `stopped_early` | The overnight run threw away 6 valid repeats (725–757 samples/s) at 8 no-aug workers, understating the baseline. |
| 2026-11-20 | Interrupted generation | Regenerate all / resume | `gen_synthetic.py --resume` | The first 10k run hit a full disk at 14.7 GB. Samples depend only on (seed, index), so missing ones can be filled in; tested to be byte-identical to a full run. |
| 2026-11-19 | Rust toolchain | MSVC / GNU on Windows | stable-x86_64-pc-windows-msvc | Rust's default on Windows; matches the CPython build ABI. Requires VS C++ tools + Windows SDK. |
| 2026-11-21 | Batch copy | Serial `collate` after decode / each worker copies into its batch slot / decode straight into the slot | Each worker copies into its slot (`par_chunks_mut`) | Profiling: serial collate cost 25 ms per batch at every thread count, more than the 19 ms parallel decode at 16 threads. Parallel copy: 686 → 978 samples/s at 16 threads, 560 → 990 at 8. Decoding straight into the slot needs a decoder that writes into a caller buffer; left for the Step 9 ablation. |
| 2026-11-21 | Windows power throttling in benchmarks | Leave to Windows / opt out | `bench.py` opts out (`SetProcessInformation`, also in DataLoader workers) and records it in the JSON | A hidden-window run was moved to E-cores mid-run (1-thread throughput halved, 12-thread doubled partway). |
| 2026-11-22 | Augmentation ranges | Baseline values fixed / baseline values as configurable defaults | Configurable from Python (`out_size`, `crop_scale`, `flip_prob`, `jitter`), defaults = bench/common.py | Like-for-like benchmark by default; usable as a library. |
| 2026-11-22 | RGB resize | Own plain bilinear / `fast_image_resize` antialiased bilinear | `fast_image_resize` 6 (Convolution Bilinear) on a cropped view | Matches torchvision `antialias=True` to ±1 level (±4 after jitter); SIMD. A crop *box* read pixels outside the crop (up to 17 levels off at the border), a cropped *view* clamps at the crop edge like crop-then-resize. |
| 2026-11-22 | Depth resize | Nearest-exact / sparse-aware min-pooling | Nearest-exact | Identical to both baselines and exact in the property test; never mixes valid and invalid. Sparse-aware pooling revisited when sparse LiDAR depth is loaded (Step 11). |
| 2026-11-22 | Rotation | Step 6 / Step 11 | Deferred to Step 11 | Not expressible in K alone (rotates the camera frame, which the LiDAR extrinsics need anyway); baselines don't rotate. |
| 2026-11-22 | Config errors in Python | RuntimeError / ValueError | New `Error::Config` → ValueError (also bad batch_size) | Bad arguments are value errors in Python convention; RuntimeError stays for worker panics. |
| 2026-11-22 | Property-test dependency | Hand-rolled random loop / `proptest` | `proptest` (dev only) | Named in CLAUDE.md §5; shrinks failures to a minimal case (checked by breaking the half-pixel term on purpose: both tests fail). |
